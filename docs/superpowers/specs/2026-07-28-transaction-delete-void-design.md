# Transaction Delete as Auditable Void

## เป้าหมาย

เพิ่มปุ่ม “ลบรายการ” สำหรับรายรับและรายจ่ายที่ผู้ใช้บันทึกผิด โดยระบบต้องย้อนผลกระทบต่อยอดบัญชี เก็บประวัติการลบ และซ่อนรายการออกจากมุมมองปกติทันที การทำงานภายในใช้สถานะ `void` ที่ระบบมีอยู่แล้ว ไม่ลบแถวการเงินจริงออกจากฐานข้อมูล

## ขอบเขต

ครอบคลุมเฉพาะรายการรายรับและรายจ่ายทั่วไปที่ผู้ใช้บันทึกโดยตรง

ไม่ครอบคลุม:

- รายการยอดยกมา
- รายการโอนเงิน
- รายการชำระค่างวดหรือปิดหนี้
- รายการที่สร้างจากรายการประจำรายเดือน
- การกู้คืนรายการที่ลบแล้ว
- การลบข้อมูลถาวรจากฐานข้อมูล

รายการที่สร้างจากโมดูลอื่นต้องแก้หรือยกเลิกผ่านโมดูลต้นทาง เพื่อไม่ให้สถานะของธุรกรรมกับสัญญาผ่อน การโอน หรือรายการประจำขัดแย้งกัน

## พฤติกรรมที่ผู้ใช้เห็น

หน้า “รายการเงิน” มีตัวกรองสองค่า:

- “รายการปัจจุบัน” เป็นค่าเริ่มต้นและแสดงเฉพาะสถานะ `posted`
- “รายการที่ลบแล้ว” แสดงเฉพาะสถานะ `void`

แต่ละรายการทั่วไปที่ยังใช้งานอยู่มีปุ่ม “ลบรายการ” เมื่อกดแล้วเปิด dialog ที่แสดง:

- ชื่อหรือหมายเหตุของรายการ
- ประเภทและจำนวนเงิน
- บัญชี
- วันที่รายการ
- ข้อความเตือนว่ายอดบัญชีจะถูกย้อนกลับ
- เหตุผลเริ่มต้น “บันทึกรายการผิด” และช่องแก้ไขเหตุผล ความยาว 1–200 ตัวอักษร

ปุ่มยืนยันใช้ข้อความ “ลบและย้อนยอด” ระหว่างส่งคำขอปุ่มทั้งหมดใน dialog ถูกปิดเพื่อป้องกันการกดซ้ำ เมื่อสำเร็จ ระบบโหลด snapshot ใหม่ ปิด dialog และรายการหายจากมุมมองปกติ

มุมมอง “รายการที่ลบแล้ว” แสดงรายการด้วยสีจาง พร้อมป้าย “ลบแล้ว” เหตุผลและเวลาที่ลบ ไม่มีปุ่มลบซ้ำหรือปุ่มแก้ไข

รายการที่มี `source` จากการโอน โมดูลผ่อน หรือรายการประจำไม่มีปุ่มลบ และแสดงข้อความว่าต้องจัดการจากโมดูลต้นทาง

## สถาปัตยกรรมและข้อมูล

ระบบใช้ endpoint เดิม:

```text
POST /v1/transactions/:id/void
{
  "version": 1,
  "reason": "บันทึกรายการผิด"
}
```

ฟังก์ชัน PostgreSQL `void_transaction` เดิมเป็นจุดเดียวที่เปลี่ยนสถานะ ย้อนยอดบัญชี เพิ่ม version และเขียน audit event จึงไม่เพิ่ม endpoint ลบถาวร

เพิ่ม migration ใหม่เพื่อแก้ `snapshot_transactions` ให้ส่งทั้ง `posted` และ `void` พร้อมข้อมูล:

- `state`
- `version`
- `voidedAt`
- `voidReason`
- `source`
- `sourceId`

ค่า `source` รองรับ `transfer_fee`, `installment_payment`, `installment_payoff` และ `recurring_occurrence` เพื่อให้เว็บแยกรายการทั่วไปออกจากรายการที่ต้องจัดการผ่านโมดูลต้นทางได้อย่างถูกต้อง

ยอดบัญชีและสรุปรายรับ/รายจ่ายยังคำนวณจากรายการ `posted` เท่านั้น การเพิ่มรายการ `void` ใน snapshot มีไว้สำหรับประวัติและไม่เปลี่ยนสูตรทางการเงิน

## ขอบเขตของโค้ด

### Contracts

- ขยาย `financeTransactionSchema` ให้รองรับ `state: "posted" | "void"`
- เพิ่ม `voidedAt` และ `voidReason` แบบ optional
- เพิ่ม `transfer_fee` และ `recurring_occurrence` ในชนิด `source`
- ใช้ `postedTransactionResponseSchema` เดิมเป็นผลตอบกลับจากการ void

### Web API

- เพิ่ม `voidTransaction(id, input)` ใน `FinanceApi`
- ให้ `RemoteFinanceApi` เรียก endpoint เดิมและตรวจผลด้วย schema ที่มีอยู่
- ใช้ version จากรายการที่กำลังลบ ไม่ค้น version จาก state ภายนอก

### UI

- `TransactionsPage` เก็บสถานะตัวกรองและรายการที่กำลังยืนยันลบ
- `TransactionList` แสดงตัวกรอง สถานะ เหตุผลการลบ และ action ที่อนุญาต
- dialog เป็นองค์ประกอบในหน้า ไม่ใช้ `window.confirm`
- หลัง void สำเร็จเรียก `onChanged()` เพื่อโหลด snapshot และยอดใหม่

## การจัดการข้อผิดพลาด

- `STALE_VERSION`: แจ้งว่ารายการถูกเปลี่ยนแล้วและโหลดข้อมูลล่าสุด
- `FORBIDDEN_WORKSPACE` หรือ `UNAUTHENTICATED`: ใช้กลไก error/session เดิม
- validation ของเหตุผล: แสดงข้อความใน dialog โดยไม่ส่ง API
- network หรือ server error: คง dialog และข้อมูลเหตุผลไว้เพื่อให้ลองใหม่
- รายการที่เป็น `void` แล้ว: ไม่มี action ใน UI และ API เดิมปฏิเสธการ void ซ้ำ

## การทดสอบ

ใช้ TDD และต้องเห็นการทดสอบใหม่ล้มก่อนเพิ่ม production code

### Contract และ database

- snapshot schema รับรายการ `posted` และ `void` พร้อม metadata
- snapshot คืนรายการที่ void แล้ว แต่ยอดบัญชีไม่นับรายการนั้น
- snapshot ระบุ source ของค่าธรรมเนียมการโอน รายการผ่อน และรายการประจำ
- void รายรับและรายจ่ายย้อนยอดอย่างถูกต้องและเขียนเหตุผล

### API client

- `voidTransaction` ส่ง id, version และ reason ไป path ที่ถูกต้อง
- response ถูกตรวจด้วย schema และ error ถูกส่งต่อรูปแบบเดิม

### UI

- ค่าเริ่มต้นแสดงเฉพาะรายการปัจจุบัน
- เปิด dialog จากรายการทั่วไปและแสดงรายละเอียดที่ถูกต้อง
- ป้องกันเหตุผลว่างและการกดซ้ำ
- เมื่อสำเร็จเรียก `onChanged` และปิด dialog
- ตัวกรองรายการที่ลบแล้วแสดงเหตุผลและไม่มี action
- รายการจากการโอน โมดูลผ่อน และรายการประจำไม่มีปุ่มลบ
- stale/network error แสดงข้อความและไม่ทำ dialog หาย

## เกณฑ์ยอมรับ

- ผู้ใช้ลบรายรับหรือรายจ่ายทั่วไปที่บันทึกผิดได้จากหน้า “รายการเงิน”
- ยอดบัญชีถูกย้อนและสรุปการเงินไม่รวมรายการที่ลบ
- รายการที่ลบหายจากมุมมองปกติ แต่ตรวจย้อนหลังได้
- ไม่มีข้อมูลธุรกรรมหรือ audit ถูกลบถาวร
- ไม่สามารถลบรายการจากโมดูลผ่อน โอนเงิน รายการประจำ หรือยอดยกมาผ่านหน้านี้
- การกดซ้ำ ข้อมูล version เก่า และข้อผิดพลาดเครือข่ายไม่ทำให้ยอดถูกย้อนซ้ำ
- ชุดทดสอบ TypeScript, database และ production build ผ่านก่อน commit implementation
